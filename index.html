Forecasting a 21.5 MW solar plant, one week ahead

Shivansh, Roll number 24110330. ES 335 Machine Learning course project, working solo.

A grid operator has to commit to a week of solar output before the weather arrives. This project asks how much a Random Forest or XGBoost forecast improves as it is given more information, and where it still fails. Pick a season, a model and a level of information below, and compare the forecast with what the plant actually produced.

The question

How accurately can tree-based ensembles forecast one week of solar power for a single utility plant, how does accuracy change as the model is given more information, and what kind of weather makes the forecast fail?

  • One row: one 15-minute reading from the plant’s SCADA logger (timestamp, power, module temperature, irradiance, air temperature, wind direction, wind speed).
  • Target: real power output, Act. Power (MW), between 0 and the 21.5 MW installed capacity.
  • When the prediction is made: once, at the start of the week, for all 672 quarter-hour steps of the next seven days. There is no re-forecasting during the week.
  • What is available then: depends on the scenario, from past power and the calendar only (S1) up to measured weather and sun position at each target time (S2 to S4). The scenarios are defined in Baseline and methods.
  • What the results can claim: how these models behaved on one plant in three specific test weeks. They show association, not cause, and they do not show how the models would do in other years, at other plants, or with a real weather forecast.

The data are SCADA logs from a 21.5 MW grid-connected solar plant in western India (western India). Data quality

  • Timestamps arrive in several text formats. The code tries eight formats and stops with an error if any timestamp cannot be parsed.
  • Duplicate timestamps are dropped. Intervals missing inside a contiguous stretch become empty values and are not filled in. A gap longer than one day starts a new block.
  • Any row with a missing feature or target is removed before modelling. This shows up as short breaks in some forecast lines, for example on the morning of 13 February in the Winter week.
  • The same rows are used for all four scenarios, so the scenarios are compared on identical timestamps.

Preprocessing

  1. Clean the time axis. Parse, sort, drop duplicates and place readings on a regular 15-minute grid (see above).
  2. Encode time of day and time of year as sine and cosine pairs, so 23:45 and 00:00 are neighbours.
  3. Build past-power features: power one day earlier (lag_1d), seven days earlier (lag_7d), and the average of the same quarter-hour over days 7 to 13 earlier (slot_mean_7_13d).
  4. Build weather features: wind speed and direction become east-west and north-south components (wind_u, wind_v).
  5. Build physics features: module-minus-air temperature, irradiance corrected for module heating (ghi_temp_interaction, using a −0.4% per °C temperature coefficient), and a wind cooling proxy.
  6. Build sun-position features: solar zenith, elevation and a clear-sky irradiance estimate computed from the date, time and the plant’s coordinates, plus a clear-sky index (measured irradiance divided by clear-sky irradiance).
  7. Fit one learned constant on training data only. A plant yield factor k_plant (MW per unit of corrected irradiance) is fitted by least squares on training rows with irradiance above 50 W/m². It feeds pv_physical_MW and clear_sky_MW.
  8. Post-process predictions. Clip to 0 to 21.5 MW and set the forecast to zero between 20:00 and 05:30, a fixed clock rule rather than something the model learns.

No scaling or imputation is applied. Trees split on thresholds, so rescaling a feature does not change them, and leaving gaps empty means there is nothing to fit on test data. The one learned preprocessing step, k_plant, uses training rows only.

One leakage exception. lag_1d is computed over the whole time axis, so for days 2 to 7 of a test week it holds the actual power of the previous test day. That is not available when a 7-day-ahead forecast is issued. The details and how many runs are affected are in Limitations.

Baseline and methods

Four levels of information

The same models are trained four times, each time with a larger feature set. S1 is the reference model: it sees only past power and the calendar, no weather, and every other scenario is compared against it.

ScenarioAddsFeatures
S1Time encodings (4) and past power (3)7
S2Measured weather at the target time: module temperature, irradiance, air temperature, wind speed, wind components (6)13
S3Physics-derived features: temperature difference, heat-corrected irradiance, wind cooling proxy (3)16
S4Sun position: zenith cosine, elevation, clear-sky irradiance, clear-sky index, two plant-yield estimates (6)22
How this differs from the proposal. The proposal described S2 as weather observed up to the forecast time and S3 as forward weather covariates. In the notebooks, S2 to S4 all use the weather measured at the target time itself, which is the same as assuming a perfect weather forecast. S3 adds derived physics features, and S4 adds sun position. The persistence and diurnal-mean baselines in the proposal are not in the notebooks, so S1 is the only reference shown here.

Two models, chosen for the data

  • Random Forest averages many decorrelated trees, which lowers variance and copes with noisy sensor readings. Each tree is fitted on training data only.
  • XGBoost adds trees one at a time, each correcting the errors of the last, with a regularised objective. It can follow sharp ramps. Training stops early when the validation error has not improved for 30 rounds.

Power depends on irradiance in a saturating, non-linear way and interacts with temperature, and the inputs have different units. Trees handle that without feature scaling. A deep model was not needed to answer this question.

Standard or greedy features

Each scenario is run twice. Standard uses every feature in the scenario. Greedy runs a forward search: starting from nothing, it repeatedly adds the one feature that gives the lowest validation RMSE, keeps going through the whole pool, rolls back to the best subset, then tries removing features that no longer help. The search itself uses a small, fast model (180 XGBoost trees, or 60 Random Forest trees of depth 10) and only ever looks at training and validation data. The search is costly: for the 22-feature pool it took about 200 to 280 seconds for XGBoost, while fitting the five final models took about ten seconds.

How the models are judged

The split is fixed before any model is compared: training weeks come first in time, then the validation month, then the final test week. Each part has one job.

Metrics shown on this site

  • MAE (mean absolute error, in MW): the typical size of a miss in physical units, without over-weighting rare large misses.
  • R² (coefficient of determination): the share of power variation the forecast explains.
  • Validation RMSE is used inside the greedy search only, because it punishes large misses more.

Both MAE and R² are averaged over all 672 steps of the week, including night hours when the forecast is zero by rule. That makes both look better than a daytime-only score would, and it is why even the weather-blind S1 model has an R² above 0.86. Read the gap between scenarios, not the absolute level.

How big a difference counts? Across all 48 runs, the five revisions of one setup differ in test MAE by a median of 0.043 MW, and by up to 0.17 MW. Differences smaller than that are not evidence that one setup is better.

Computed but not shown. The notebook code also calculates RMSE, daytime MAPE, mean bias, daytime MAE and the share of 15-minute blocks inside the ±7% Deviation Settlement band, and writes them to CSV files. Those values were not printed in the saved notebook output, so they are not on this site. Re-running the notebooks produces them.

What the numbers say

  • Adding measured weather (S1 to S2) is the big step. Test MAE falls by 14% to 31% in Summer, 26% to 43% in Winter, and 44% to 74% in Monsoon, depending on model and feature mode.
  • After S2, the gains are small and uneven. Summer XGBoost with all features gets worse from S3 (0.771 MW) to S4 (0.817 MW), and Summer Random Forest with greedy features is worse at S3 (0.836 MW) than at S2 (0.692 MW). Typical changes after S2 are close to the 0.043 MW revision spread, so S2, S3 and S4 cannot be ranked from one test week.
  • Greedy features beat all features in 20 of 24 matched pairs on test MAE, usually with fewer inputs. The four exceptions are Summer Random Forest S3, Monsoon XGBoost S1, Monsoon Random Forest S1 and Monsoon Random Forest S4, where the greedy set was worse.
  • Validation points to one setup. In all three seasons the lowest validation MAE among the 16 runs of each season belongs to XGBoost S4 with greedy features, which scores 0.671 MW (Summer), 0.451 MW (Winter) and 0.393 MW (Monsoon) on the test week. XGBoost’s validation numbers are slightly flattered because early stopping used the same validation data.
  • Models fit training data much better than new data. Test MAE is on average 0.25 MW above training MAE for XGBoost and 0.37 MW for Random Forest. Switch the measure to “Train MAE” above to see it.
  • Test MAE is lower than validation MAE in Summer (14 of 16 runs) and Monsoon (all 16), but never in Winter. The test week is a single week, so this reflects that week and not better generalisation.

Where the forecasts fail

Four representative cases, each read from the forecast plots. These describe what is visible in the plots; they are patterns to check, not proven causes.

Limitations

  1. The previous-day power feature leaks test data. lag_1d is the power one day earlier. For days 2 to 7 of the test week, that is actual power from inside the test week, which would not exist when a 7-day forecast is issued. Of the 48 runs, 39 include it (every Standard run, plus the Greedy runs marked below). The size of the effect is unknown without re-running. Because S1 depends on past power the most, S1 is probably flattered, so the S1-to-S2 improvement is more likely understated than overstated. The fix is to drop lag_1d and re-run. The plot titles saved by the notebook say “no test-period lags”, which is not accurate for runs that use this feature.
  2. Weather is measured, not forecast. S2 to S4 use the weather recorded at the target time. A real operator would have only a weather forecast, which has its own error. These results are closer to a best case.
  3. Only one reference model. S1 is the only comparison point. Persistence (“same as yesterday”) and the average daily curve were proposed but are not in the notebooks, so there is no check that the tree models beat the simplest rules.
  4. One test week per season. There are no confidence intervals, and a single cloudy or clear week can change a ranking. The revision spread is the only uncertainty measure shown.
  5. Metrics include night. MAE and R² are diluted by hours of exact zeros. Daytime-only results and bias exist in the code but not in the saved outputs.
  6. Seasons are modelled separately, each from about three months of history. Nothing here shows how a model would transfer to another season or another plant.
  7. No causal claim. A feature that helps prediction is not shown to cause higher output.

Which runs use the previous-day feature?

A red dot means lag_1d is in the model’s inputs. Standard runs always include it. Greedy runs include it only if the search kept it.

Conclusion

Telling a week-ahead solar forecast what the weather will be matters far more than which tree model is used or how many derived features are added. Moving from calendar and past power only (S1) to measured weather (S2) cut test MAE by 14% to 31% in Summer, 26% to 43% in Winter, and 44% to 74% in Monsoon. Beyond that, the remaining differences between feature sets and between Random Forest and XGBoost are mostly within the spread between revisions of the same model.

The forecasts still fail in recognisable ways: they miss fast cloud swings when they cannot see the weather, run a little low on clear days in Winter, and echo yesterday’s pattern when yesterday’s power is the main clue. Because the weather inputs are perfect measurements and one input leaks a day of test power, these numbers describe a best case. The honest next steps are to remove lag_1d, add the simple baselines, and replace measured weather with a forecast of it.

Reproduce this work

  1. Get the plant data from the Power Systems and Smart Grid Laboratory, IIT Gandhinagar, with permission. It is not included here.
  2. Create one training, validation and test CSV per season with the columns listed under The data. The notebooks expect these file names:
    Summer: Summer_Training.csv, Summer_Validation.csv, Summer_Testing.csv Winter: Winter_Dataset_Train.csv, Validation_Dataset_Winter.csv, Testing_Dataset_Winter.csv Monsoon: Monsoon_Train.csv, Monsoon_Validation.csv, Monsoon_test.csv
  3. Install the libraries: pip install numpy pandas matplotlib scikit-learn xgboost, or use requirements.txt.
  4. Open one notebook from the code folder and run all cells. Each one runs 16 setups (2 models × 4 scenarios × standard or greedy), five revisions each. The greedy searches dominate the run time, at about 12 to 15 minutes per season in the saved runs (on the author’s machine).
  5. Results are written to final_deliverables/, with a forecast CSV, a Deviation Settlement CSV, a metrics CSV and an overlay plot for every setup.

Random seeds are fixed in the revision settings. The notebooks are provided with their outputs cleared. This site’s numbers and plots were read directly from the saved outputs of the original runs.
